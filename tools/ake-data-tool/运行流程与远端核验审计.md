# AKE Data Tool 运行流程与远端核验审计

> 审计日期：2026-08-24  
> 审计范围：`tools/ake-data-tool` 当前源码、启动脚本和配置结构  
> 审计方式：静态调用链审计；未执行真实下载、解析、发布或 R2 写入  
> 不在范围内：父项目网页模块、`public/TableCfg/**` 与 `public/Json/**` 的数据内容、`beyond-sdk.jar` 内部实现

## 1. 结论摘要

AKE Data Tool 实际包含七条主要业务链路：

1. TableCfg 手动更新：官方版本查询 → 索引/资源准备 → beyond-sdk 本地解包 → 本地校验 → 发布到 `public` → 可选上传 R2。
2. TableCfg 自动监听：定时查询 Seed/Hotfix，发现新版本后执行 TableCfg 更新链路。
3. 图片部分解析（`standard`）：准备 Bundle/InitialBundle/BundleManifest VFS → 读取 standard 历史 map → 原生 hash 差分 → 增量导出 → 发布到 `public/images`。
4. 图片完整解析（`full`）：准备相同 VFS → 同时读取 full 与 standard 历史 map → 联合历史 hash 差分 → 增量导出 → 发布到 `public/images`。
5. Json 解析：准备 TableCfg/Json/InitialExtendData/ExtendData VFS → beyond-sdk 导出 → 发布六类 Json 数据目录。
6. 图片/Json 资产同步：以 `https://data.akedata.wiki/asset-sync-index.json` 为远端置信源进行路径、大小、MD5 差异比较，再定向写入 R2 并更新索引；图片同步后再提交 Asset map。
7. 云端图片配置与 R2 版本管理：从资产索引读取/写入双 profile 配置；读取、删除 TableCfg 版本及其根 `manifest.json` 记录。

当前资产同步不会统计或遍历整个 R2 桶。容量、文件数和差异均来自 `asset-sync-index.json`；R2 侧只对精确对象或精确目录执行 `cat`、`copy`、`copyto`、`delete`、`purge`、`lsf`。

远端交互中，只有一部分属于“核验”：

- Seed、Hotfix、索引和资源请求主要是远端数据获取；响应状态、结构、大小、MD5 是获取结果的完整性核验。
- 资产正式同步前和写入期间再次读取 `asset-sync-index.json`，属于并发/新鲜度核验。
- TableCfg 上传后再次读取根 `manifest.json`，以及版本删除后回读 manifest、检查目录为空，属于上传后/删除后远端核验。
- 资产索引、图片 map 和 map manifest 上传后目前没有远端回读，仅依赖 rclone 退出码。

## 2. 标记约定

本文使用以下标记：

| 标记 | 含义 |
| --- | --- |
| **[远端获取]** | 从官方 API、CDN、data 站或 R2 读取信息/文件，主要目的是取得输入。 |
| **[远端核验]** | 读取远端状态并与本地预期或先前状态比较。 |
| **[远端并发核验]** | 发布前重新读取远端索引，防止覆盖其他发布者的更新。 |
| **[远端写入]** | 向 R2 上传、删除或更新对象。 |
| **[本地核验]** | 只读取本地文件、摘要、状态或目录，不产生网络请求。 |
| **[间接远端]** | 网络行为可能发生在 `beyond-sdk.jar` 内部，本项目源码不能完全审计。 |

“官方版本核验”特指 Seed/Hotfix 接口。读取 data 站资产索引或 map manifest 不属于官方版本核验。

## 3. 总体结构与状态流

```text
run-gui.bat / python -m ake_tool.cli
                  │
                  ├─ GUI worker ───────────────┐
                  ├─ CLI check/run/stage       │
                  │                            │
                  ├─ Pipeline                  │ TableCfg
                  ├─ ImageAssetPipeline        │ 图片 / Json
                  └─ ReleaseManager            │ R2 / 资产索引 / map
                                               │
官方 Seed/Hotfix ──> 版本与资源地址 ────────────┤
官方 main/initial ─> 解密索引 ─> VFS 文件清单 ─┤
游戏目录/工作缓存 ─> 本地复用 ──────────────────┤
data 站索引/map ──> 差分基线与云端配置 ─────────┤
                                               ▼
工作目录 state / image-state / pending 标记 ─> public ─> R2
```

### 3.1 核心本地状态

| 文件或目录 | 写入者 | 用途 |
| --- | --- | --- |
| `<image_work_dir>/state.json` | `StateStore` / TableCfg 流水线 | 保存当前 Hotfix、已完成步骤、工作目录和 R2 发布结果。 |
| `<image_work_dir>/image-state.json` | `ImageAssetPipeline` / `ReleaseManager` | 保存图片与 Json 版本信息、各 profile 发布授权、map 摘要、map 是否已提交。 |
| `<image_work_dir>/indexes/<version>/` | 图片/Json分析 | 缓存已解密 main/initial 索引。 |
| `<image_work_dir>/hotfix-cache/<version>/` | 图片/Json准备 | 缓存从 Hotfix 下载的 VFS 文件。 |
| `<image_work_dir>/VFS/` | 图片/Json准备 | 独立 VFS 工作副本；禁止链接文件。 |
| `<image_work_dir>/output/<profile>/` | 图片解析 | 分 profile 持久保存增量图片输出。 |
| `<image_work_dir>/image-runs/<profile>/<runId>/` | 图片解析 | 保存本次 full/delta/remote map 和临时增量输出。 |
| `<image_work_dir>/map-cache/` | `AssetMapHistoryLoader` | 保存经 size+SHA256 核验的历史 map。 |
| `<image_work_dir>/asset-sync-pending.json` | 资产同步 | 标记一次资产索引同步正在进行。 |
| `<image_work_dir>/release-pending/` | TableCfg 上传 | 允许继续完成“数据已上传但 manifest 未提交”的任务。 |
| `<image_work_dir>/r2-delete-pending/` | R2 版本删除 | 允许继续清理“manifest 已移除但目录未删完”的版本。 |

状态文件只用于本地恢复和授权，不是远端置信源。资产差异每次重新读取 data 站最新索引；不会保存远端资产索引快照作为下次比较基线。

## 4. 入口与界面调度

### 4.1 启动脚本

- `run-gui.bat`：优先使用 `.venv\Scripts\python.exe`，否则使用系统 Python，执行 `python -m ake_tool.cli gui`。
- `setup-venv.bat`：创建 `.venv` 并安装 `requirements.txt` 中的 `requests` 与 `PyQt6`。
- `ake_tool/__main__.py`：将 `python -m ake_tool` 转交给 `cli.main()`。
- `ake_tool/__init__.py`：只声明包说明和内部版本 `0.1.0`，不参与业务流程。

### 4.2 CLI

`ake_tool/cli.py` 提供：

| 命令 | 调用 | 远端行为 |
| --- | --- | --- |
| `check` | `Pipeline.check_latest()` | 官方模式请求 Seed+Hotfix；手动模式只请求指定版本 Hotfix。 |
| `run` | `Pipeline.run()` 或指定 `--steps` | 进入完整/选择的 TableCfg 流水线；即使未选择 `check`，也会先调用 `check_latest()`。 |
| `stage <name>` | `Pipeline.run_steps([name])` | 单步骤仍会先查询版本。 |
| `config` | 读取并打印本地配置 | 无远端访问。 |
| `gui` | `gui.run_gui()` | 启动图形界面。 |

### 4.3 GUI worker

`ake_tool/gui.py` 不直接实现业务，而是把任务放入互斥的 `QThread`：

| Worker | 业务对象 | 操作 |
| --- | --- | --- |
| `PipelineWorker` | `Pipeline` | TableCfg 查询或所选步骤。 |
| `ImageAssetWorker` | `ImageAssetPipeline` | 图片 standard/full 或 Json 四步流程。 |
| `AssetUploadWorker` | `ReleaseManager` | 资产差异计划与正式同步。 |
| `ImageConfigWorker` | `CloudImageConfigLoader` / `ReleaseManager` | 云端图片配置读取或同步。 |
| `R2VersionWorker` | `ReleaseManager` | R2 TableCfg 版本列表与删除。 |
| `AutoWatchWorker` | `HotfixClient` + `Pipeline` | 周期性检查并自动更新 TableCfg。 |

GUI 会阻止 TableCfg、图片/Json、资产、R2 管理和监听任务并发运行。配置保存、按钮资格和用户确认发生在 worker 启动前。

界面现有说明有一处与实现不一致：`gui.py` 的资产页仍写着“读取 R2 根目录 asset-sync-index.json”，当前实现实际读取 `data.akedata.wiki`，R2 仅是最终写入目标。

## 5. TableCfg 手动更新流程

实现入口：`ake_tool/pipeline.py::Pipeline`。固定步骤为 `check → download → unpack → validate → publish → upload`。

### 5.1 所有选择方式共有的前置行为

`Pipeline.run_steps()` 会先去重并校验步骤，再无条件执行 `check_latest()`。因此：

- 仅运行 `validate`、`publish` 或 `upload` 也会访问官方接口。
- `check` 不在选择列表时，查询结果不单独记录为完成步骤，但仍决定 job 目录和后续版本。
- 同一 `Pipeline.run_steps()` 内后续步骤沿用这一次取得的 `LatestInfo`，发布到 `public` 前不会再次查询 Hotfix。

### 5.2 check：确定版本

官方模式：

1. **[远端获取]** POST Seed API，取得游戏包路径。
2. **[本地核验]** 从包路径解析游戏版本、Seed 版本和 `rand_str`；缺字段或格式不符即失败。
3. **[远端获取]** GET Hotfix API，取得 `resVersion`、main/initial 的版本和资源根地址。
4. **[本地核验]** 响应必须包含 main 与 initial 两部分。

手动版本模式：

1. 使用配置中的 `manual_seed_version` 与 `manual_rand_str` 构造 SeedInfo。
2. 跳过 Seed API。
3. **[远端获取]** 只请求该指定游戏版本对应的 Hotfix API。

这里的 HTTP 状态与响应结构检查是“获取结果校验”，不是发布前复查。

### 5.3 download：索引与 VFS 输入准备

1. 对 main、initial 分别执行：
   - **[远端获取]** 下载加密的 `index_main.json` / `index_initial.json`。
   - **[本地核验]** 尝试候选密钥解密，并要求结果是包含 `files` 的 JSON 对象。
   - 为 beyond-sdk 写入带 `version`、`isInitial` 信息的本地索引副本。
2. 从两份索引筛选 TableCfg 区块，合并同名条目。
3. 读取游戏 `StreamingAssets` 与 `Persistent` 中的本地索引。
4. **[本地核验]** 先比较本地索引记录与最新索引记录的 size+MD5；匹配时复制游戏文件。
5. 对每个目标文件：
   - **[本地核验]** 已存在目标必须不是链接、大小正确、MD5 正确，才允许复用。
   - **[远端获取]** 缺失或校验失败时从对应 Hotfix 根地址下载，支持 Range 续传和重试。
   - **[本地核验]** 下载完成后检查最终大小和 MD5，再原子替换 `.part` 文件。
6. **[本地核验]** 整个 SDK 输入目录不得包含硬链接、符号链接或目录联接。

注意：游戏目录候选在选择时主要依赖索引元数据匹配，复制后会由 `DownloadManager` 对工作目标再做实际大小/MD5 核验。

### 5.4 unpack：beyond-sdk 本地解包

1. **[本地核验]** 检查 Java、`beyond-sdk.jar`、VFS、两份索引和 IL2CPP runtime 缓存。
2. 缺少 runtime 文件时直接失败，明确拒绝让 SDK 自动下载。
3. `BeyondSdkTableRunner.java` 构造 TaskGraph，并强制：
   - 不存在 `fetchVFSHotfix`；
   - `unpackTableCfg` 只依赖 `useLocalVfs`；
   - `useLocalVfs` 自身没有依赖。
4. 只运行 `unpackTableCfg`，完成后定位输出的 `TableCfg` 目录。

此步骤按当前启动器设计为本地流程，没有本项目主动发起的远端请求。

### 5.5 validate：工作结果校验

全部为 **[本地核验]**：

- `TableCfg` 目录存在；
- 至少存在 JSON 文件；
- 配置的必需表存在；
- 所有 JSON 能被解析；
- 返回表文件数量。

### 5.6 publish：发布到 public

1. **[本地核验]** 再次执行 TableCfg 内容校验。
2. 复制到同级 staging 目录。
3. 用目录替换方式发布到 `public/TableCfg`。

此步骤没有远端请求，也不会复查官方最新 Hotfix。

### 5.7 upload：上传 TableCfg 到 R2

1. **[本地核验]** 上传前再次校验 `public/TableCfg`。
2. 沿用本次流水线 `check_latest()` 的版本；不再次请求 Seed/Hotfix。
3. **[远端获取/核验]** 对精确版本目录执行 `rclone lsf --max-depth 1`，判断目录是否已有数据。
4. **[远端获取/核验]** `rclone cat` 根 `manifest.json`，判断版本记录和 `latest`。
5. 若目录、版本记录以及 `latest` 状态已满足要求，跳过重复上传。
6. 目录存在但 manifest 无记录、且没有本工具 pending 标记时，拒绝覆盖。
7. **[远端写入]** 目录不存在时以 `--immutable` 上传 TableCfg，并写本地 pending 标记。
8. 构造新根 manifest。手动历史版本默认不切换 `latest`；显式勾选后才切换。
9. **[远端写入]** 上传根 `manifest.json`。
10. **[远端核验]** 再次 `cat` 根 manifest，核对 `latest` 和目标版本记录；通过后删除 pending 标记。

风险边界：上传前的 `lsf` 和 `cat` 使用允许失败模式，网络、鉴权等错误可能被当成“目录/manifest 不存在”；后续上传通常仍会失败，但前置诊断可能不准确。上传后只回读 manifest，不逐文件回读 TableCfg 内容。

## 6. TableCfg 自动监听流程

实现入口：`gui.py::AutoWatchWorker`。

1. 从 `state.json` 读取上次完成到 `publish` 或 `upload` 的 Hotfix 版本。
2. 每隔 `watch_interval` 秒：
   - **[远端获取]** 调用 `HotfixClient.get_latest()`，即 Seed POST + Hotfix GET。
   - 与本地 `processed_version` 比较。
3. 首次没有已发布状态时只建立基线，不立即更新。
4. 发现变化后，根据配置执行 `download、unpack、validate、publish`，可选追加 `upload`。
5. 已在同版本 state 中完成的步骤会被跳过。
6. 自动任务强制关闭手动版本和手动切换 latest。

需要特别标记的重复远端访问：监听 worker 已取得一次 `LatestInfo`，但随后新建 `Pipeline.run_steps()`；后者会再次执行 `check_latest()`。因此每次真正触发更新时通常会连续调用两轮 Seed+Hotfix。第二轮结果才是流水线实际使用的版本。

## 7. 图片解析（standard）流程

实现入口：`ake_tool/image_assets.py::ImageAssetPipeline`，profile 为 `standard`。

### 7.1 image_analyze：版本与来源规划

1. **[远端获取]** 调用一次 Seed+Hotfix，取得本次图片解析版本。
2. **[远端获取]** 分别下载并解密 main、initial 索引。
3. 同一 Hotfix 的索引下载失败时，允许使用已存在的同版本本地索引缓存；不存在缓存则失败。
4. 从索引提取 Bundle、InitialBundle 与 BundleManifest 条目；所有条目必须带 MD5。
5. 读取游戏 StreamingAssets/Persistent 索引，按 size+MD5 元数据选择本地来源。
6. **[本地核验]** 对 Hotfix 缓存候选实际计算 size+MD5；匹配才标为 cache。
7. 输出本地可复用、缓存可复用和需要远端下载的数量/字节数。

同一个 `ImageAssetWorker` 一次勾选多个步骤时，资源计划缓存在内存中，后续 `image_prepare` 沿用 Seed、Hotfix 和索引结果。若用户把步骤拆成多个独立任务，每次都会创建新 pipeline，分析/准备可能重新请求官方接口和索引。

### 7.2 image_prepare：下载与独立 VFS 组装

1. 取得/沿用 analyze 的资源计划。
2. **[本地核验]** 遍历工作目录现有 VFS：只有文件名、大小和 MD5 都与最新索引一致且不是链接时，才直接复用，不再复制组装。
3. **[远端获取]** 下载仍标记为 remote 的 VFS 文件；每个文件结束后核对大小与 MD5。
4. 从 workspace、StreamingAssets、Persistent 或 Hotfix cache 复制剩余文件到独立工作 VFS。
5. 删除当前区块中已不在最新索引里的旧工作文件。
6. **[本地核验]** 组装后检查每个目标文件；失败时从 Hotfix 重新下载该文件并再次校验。
7. **[本地核验]** 工作 VFS 不得含链接文件。

该步骤没有“VFS 完成后复查官方版本是否变化”。它只校验本次已确定版本对应的文件完整性。

### 7.3 image_extract：历史 map 差分与导出

1. 从 `image-state.json` 读取 prepare 已确认的版本；不请求 Seed/Hotfix。
2. **[本地核验]** 要求 VFS 完整、独立且不存在链接。
3. 解析 VFS key：
   - GameAssembly 大小和修改时间与 key 缓存记录一致时直接复用。
   - 否则运行 `BeyondSdkVfsKeyRunner.java`。
   - **[间接远端]** Runner 调用 SDK 的 `VfsKeyResolver.resolveForProcessLifetime()`；本项目未限制其内部网络行为，是否下载 IL2CPP runtime 取决于 beyond-sdk 实现与本地缓存。
4. **[远端获取/核验]** 从 data 站读取 `/map/manifest.json`：
   - HTTP 404：认定尚无任何 map，允许首次 bootstrap；
   - manifest 存在但缺 standard profile：只对 standard 视为 bootstrap；
   - HTTP 403、其他 HTTP 错误、网络错误、无效 JSON 或结构错误：直接失败，拒绝退化为全量解析。
5. 若 standard 历史 map 存在：
   - **[本地核验]** 本地 map 缓存必须同时匹配 manifest 的 size 与 SHA256；
   - 缓存未命中时 **[远端获取]** 下载 map，并核对 size+SHA256 后原子缓存。
6. 运行 `BeyondSdkImageRunner.java`：一次构建当前完整 map、一次原生 hash 差分、最多一次导出 delta。
7. Java 侧核验历史 map 可原生解码，并将有效历史 `AssetEntry.hash` 合并为跳过集合。
8. Python 侧 **[本地核验]**：
   - full/delta/remote 三份 map 均存在且非空；
   - SDK 返回的历史条目数与 manifest 一致；
   - bootstrap 时 delta 必须等于 full；
   - delta 非空时必须确有导出文件；
   - 输出目录不存在链接。
9. 把 delta 图片按 size+MD5 合并到持久输出，不删除历史图片。
10. 记录 jar SHA256、输出树摘要、三份 map SHA256和发布授权。

### 7.4 image_publish：发布图片到 public

全部是本地操作：

1. **[本地核验]** profile、配置摘要、runId 和已完成步骤必须与授权一致。
2. **[本地核验]** 重新计算 full/delta/pending map SHA256、beyond-sdk.jar SHA256 和输出树摘要。
3. **[本地核验]** 输出范围由当前 `ImagePathMatcher` 过滤；路径必须在受控目录内且不存在链接。
4. 按 size+MD5 判断新增、覆盖、未变化，并复制到 `public/images/assets`。
5. 不删除任何历史图片，也不触碰 profile 范围外文件。

此步骤不复查官方版本，不读取 data 站，不访问 R2。

## 8. 图片解析（完整，full）流程

`full` 与 `standard` 共用 analyze、prepare、VFS key、导出和发布机制，区别在配置范围与历史 map 基线：

1. 使用 full profile 的独立正则配置和授权状态。
2. **[远端获取/核验]** 一次读取同一个 data 站 map manifest。
3. 同时解析 full 与 standard 两条 manifest 记录。
4. 两份历史 map 各自按本地缓存 size+SHA256 复用，未命中时分别下载并核验。
5. 将 full 历史 hash 与最新 standard 部分解析 map 的历史 hash 联合，只有同时不在两者中的当前图片才进入 delta。
6. full profile 缺失但 standard 存在时，不是完全 bootstrap；standard 历史仍会参与去重。
7. 只有 full 与 standard 比对历史均不存在时，才把当前完整 map 全部视为增量。
8. full 与 standard 的发布授权、map 文件名和 manifest profile 相互独立。

full 的 `image_publish` 同样是纯本地发布，不复查官方 Hotfix。

## 9. Json 解析流程

Json 使用同一个 `ImageAssetPipeline`，但区块和输出不同。

### 9.1 json_analyze

1. **[远端获取]** 查询一次 Seed+Hotfix。
2. **[远端获取]** 下载并解密 main/initial 索引。
3. 提取 TableCfg、Json、InitialExtendData、ExtendData 区块。
4. 规划 StreamingAssets、Persistent、Hotfix cache 与远端来源。
5. **[本地核验]** Hotfix cache 候选按 size+MD5 实际核验。

### 9.2 json_prepare

1. **[本地核验]** 检查工作 VFS 中可按文件名、size、MD5 直接复用的文件。
2. **[远端获取]** 下载剩余 Hotfix 文件并校验 size+MD5。
3. 组装独立 VFS；失败项回退 Hotfix 下载。
4. **[本地核验]** 完成后再次逐文件检查 JSON SDK 输入。

当前实现存在额外本地成本：组装循环已经核验过的目标，在 prepare 末尾仍有一轮最终逐文件 size+MD5 检查；这不会访问远端，但大型 VFS 会产生重复磁盘读取。

### 9.3 json_extract

1. 从状态读取 prepare 已确认版本，不查询官方接口。
2. **[本地核验]** 只检查状态、VFS、索引与 SDK 任务是否可用，不重新执行整套 analyze。
3. 为 beyond-sdk 准备 main/initial 索引。
4. 从 jar 中检测可用的 `unpackJson` 或 `exportJsonData` 任务。
5. 启动 beyond-sdk，并传递 `--no-vfs-update`，使用本地 VFS 导出。

Python 代码没有直接远端请求；jar 是外部边界，但启动参数明确要求不更新 VFS。

### 9.4 json_publish

1. **[本地核验]** 检查提取状态和预期来源目录。
2. 通过 staging/替换发布下列六个数据集：`BuffData`、`LevelData`、`LevelScriptData`、`MissionRuntimeAsset`、`SkillData`、`SpawnerConfig`。
3. 不查询官方版本，不读取 data 站，不访问 R2。

## 10. 图片云端配置流程

### 10.1 启动读取

当启用“读取云端配置”时，GUI 启动异步 `ImageConfigWorker(load)`：

1. **[远端获取]** 以时间戳 query 和 no-cache 请求读取 `https://data.akedata.wiki/asset-sync-index.json`。
2. **[本地核验]** HTTP 必须成功、JSON 可解析、移除 `imageParsingConfigs` 后的资产索引主体结构有效。
3. 对 standard/full 分别解析 `ImageParsingConfig`。
4. 网络失败、403、超时、无效 JSON 或索引结构错误：两个 profile 都回退本地配置。
5. 单个 profile 缺失/无效：只对该 profile 回退本地配置。

因此日志中的“本地配置：等待读取云端配置”只是异步占位；“本地配置（云端请求失败）”表示容错回退，不会阻止后续图片任务。

### 10.2 同步配置到云端

1. **[远端获取]** 读取 data 站最新资产索引并记录完整索引 digest。
2. 在本地替换指定 profile 配置，更新索引 revision/updatedAt。
3. **[远端并发核验]** 上传前再次读取 data 站索引；digest 与首次不同即拒绝覆盖。
4. **[远端写入]** 通过 rclone 上传 R2 根 `asset-sync-index.json`。
5. 当前没有上传后从 R2 或 data 站回读核验，只依赖 rclone 退出码。

## 11. 图片/Json 资产差异比较

实现入口：`ReleaseManager.plan_asset_sync()`。

1. 本地要求 rclone 可执行文件存在；即使比较本身只读 data 站，也会提前检查 rclone。
2. **[远端获取]** 每次从 data 站读取最新 `asset-sync-index.json`；本地快照比较模式已被明确禁用。
3. **[本地核验]** 解析并严格校验资产索引路径、数据集、size、MD5、revision 和可选图片配置结构。
4. 扫描本地 `public/images` 和/或 `public/Json`，为每个文件计算 size+MD5。
5. 以路径为键比较：
   - 远端无路径：upload；
   - 路径相同但 size/MD5 不同：overwrite；
   - 本地无路径：delete。
6. 图片只比较当前 profile 正则范围，并强制清空 delete 列表；历史图片不会被删除。
7. Json 忽略子目录兼容 `manifest.json`，允许删除远端索引中的多余项。
8. 选择图片时：
   - **[本地核验]** 要求当前图片发布授权、profile 和配置摘要有效；
   - 沿用图片解析阶段记录的正式资产版本，不请求官方 API；
   - map 上传版本可使用手动值，如 `1.4.4@12345678-1`，该值只影响 map 文件名和 manifest 版本，不影响解析数据或 Hotfix。
9. 只选择 Json 时：**[远端获取]** 调用 Seed+Hotfix 取得正式资产版本。
10. 容量统计只汇总索引中的 size，不读取桶；超过 10 GB 只提醒，不阻止上传。

比较结果包含远端索引 revision+digest、完整路径列表和本地扫描记录；正式同步必须复用该计划。

## 12. 图片/Json 资产正式同步

实现入口：`ReleaseManager.sync_assets()`。

### 12.1 发布前资格与版本检查

1. **[本地核验]** 计划必须来自 remote compare，选择、路径、远端目标、图片配置摘要均不得变化。
2. 图片计划：
   - 只读取图片状态，不重新哈希解析产物；
   - 沿用解析阶段正式资产版本；
   - 核对 runId、pending map digest、条目数和手动 map 版本没有变化；
   - 不请求 Seed/Hotfix。
3. 纯 Json 计划：**[远端核验]** 正式同步前再次调用 Seed+Hotfix，并要求资产版本仍等于比较时版本。这是当前仍存在的官方版本复查。
4. **[远端并发核验]** 从 data 站重新读取资产索引，要求 revision+digest 与比较计划完全一致。

### 12.2 定向资产写入

1. 写入本地 `asset-sync-pending.json`。
2. 如果资产无变化，跳过图片/Json对象写入；若有图片 map，仍可继续提交 map。
3. Json：
   - **[远端写入]** 按 `delete_paths` 定向删除；
   - **[远端写入]** 按 upload+overwrite 路径清单执行 rclone copy。
4. 图片：
   - 禁止 delete；
   - **[远端写入]** 只上传 upload+overwrite 路径，使用 `--files-from-raw --no-check-dest --no-traverse`；
   - 不在上传前查询单个对象，不在上传后逐个回读。
5. 资产传输成功后在本地合并生成下一版索引。
6. **[远端并发核验]** 再次读取 data 站最新索引；若与同步开始时不同，拒绝覆盖索引。
7. **[远端写入]** 上传新的 R2 根 `asset-sync-index.json`。

这里三次 data 站读取分别发生在“比较”“正式同步开始”“资产写入结束”。前两次防止使用过期计划，第三次覆盖完整资产传输窗口。它们不是桶枚举，但每次都会下载完整索引文件。

并发失败边界：第三次读取发现变化时，资产对象已经写入，索引不会更新；因此可能留下未被索引引用的新对象或覆盖内容，需要重新比较和同步来收敛。

### 12.3 Asset map 提交

1. **[本地核验]** pending map 文件必须存在且 SHA256 与图片授权一致。
2. **[远端获取/核验]** 通过 rclone 读取 R2 `map/manifest.json`：
   - 明确的 not found 或空内容：按首次 bootstrap 建空 manifest；
   - 其他 rclone 错误：失败；
   - 无效 JSON/结构：失败；
   - 同 profile、同版本但摘要不同：拒绝覆盖。
3. **[远端写入]** 先上传不可变版本 map 文件。
4. **[远端写入]** 再上传更新后的 `map/manifest.json`。
5. 更新本地图片状态为 map committed，禁止同一解析授权重复提交。

当前缺口：map 文件和 manifest 上传后均没有回读；读取 manifest 与写入之间也没有第二次并发核验，同时发布不同 profile 时存在后写覆盖前写 manifest 的理论窗口。

### 12.4 完成与容量提示

最终文件数和容量仍从本地合并后的索引汇总。超过 10 GB 仅发出提醒。没有 `rclone size`、全桶 `lsf` 或 `rclone check`。

## 13. R2 TableCfg 版本管理

### 13.1 读取版本列表

1. **[远端获取]** `rclone cat <bucket>/manifest.json`。
2. **[本地核验]** 根节点必须是对象，`versions` 必须是数组。
3. 返回 `latest`、`updatedAt` 和版本记录。

不枚举版本目录，也不验证 manifest 中每个目录真实存在。

### 13.2 删除版本

1. **[远端获取/核验]** 严格读取根 manifest。
2. **[本地核验]** 目标版本 ID 与 manifest 中 gameVersion/hotfixVersion 必须安全且一致。
3. 写本地删除 pending 标记。
4. **[远端写入]** 先上传不再引用目标版本的新 manifest。
5. **[远端核验]** 回读 manifest，确认版本已移除且 `latest` 与预期一致。
6. **[远端写入]** purge 精确 TableCfg 版本目录。
7. **[远端核验]** 对该精确目录执行 `lsf --max-depth 1`，必须为空。
8. 删除本地 pending 标记。

先改 manifest 再删目录的顺序保证删除失败时只留下线上不可见的孤立目录；pending 标记允许再次精确清理。

## 16. 重复核验与耗时热点

### 16.1 明确存在的重复远端请求

1. 自动监听：检测新版本时 Seed+Hotfix 一轮，进入 Pipeline 后又一轮。
2. 纯 Json 资产：差异比较时 Seed+Hotfix 一轮，正式同步前再一轮。
3. 资产索引：比较一次、正式同步开始一次、资产写入后一次。三次目的不同，但都下载完整约数 MB 索引。
4. 云端图片配置：GUI 启动读取一次；用户稍后做资产比较时会另行读取，不共享响应。
5. 把图片/Json四步拆成多个任务：内存资源计划不跨 worker 保存，analyze/prepare会重新查版本和索引。

### 16.2 主要本地耗时，不是带宽

1. 图片/Json analyze 会对 Hotfix cache 候选计算完整 MD5；缓存文件很大时，日志可能停留在“下载并解密索引”之后，看起来像网络卡住。
2. prepare 会对工作 VFS 做一轮按文件 MD5 复用判断，再做组装后完整性检查。
3. Json prepare 还有最终 SDK 输入逐文件核验，存在重复读取。
4. 图片 extract 会计算 map SHA256、输出树摘要、增量合并 MD5；publish 再重新计算授权相关摘要。
5. 资产比较会扫描所选 public 数据集并计算所有本地文件 MD5；远端只下载索引，不读取桶对象。

### 16.3 `正在上传图片新增或变更项` 的耗时来源

该日志出现后执行的是一次定向 rclone copy：

- 只包含计划中的新增/变更路径；
- 使用 `--no-check-dest --no-traverse`，不会统计桶或逐对象预查；
- 该区间主要包含本地读取、到 R2 的实际上传、TLS/S3请求开销、rclone并发/重试和服务端响应；
- 当前代码在这条日志与“上传完成”之间没有额外 MD5、桶枚举或上传后逐文件核验。

因此这段时间若显著过长，首要排查实际文件总字节数、小文件数量、R2/S3请求延迟、rclone传输日志和重试；不能只根据“69个”判断带宽，69个大文件与69个小文件成本完全不同。

## 17. 核验缺口与风险分级

### 高优先级

1. **资产索引上传无回读**：资产对象写完并上传新索引后，只依赖 rclone 退出码，界面“索引校验通过”的文字强于实际保证。
2. **map manifest 并发窗口**：只在上传 map 前读取一次 manifest；map和manifest写入后无回读，多发布者可能覆盖其他 profile 的 manifest 更新。
3. **资产写入与索引不是原子事务**：传输期间发现索引并发变化会拒绝索引覆盖，但已写对象不会回滚。

### 中优先级

1. 自动监听重复获取官方版本，增加延迟并可能在两次请求间遇到版本切换。
2. 纯 Json 资产正式同步前仍复查官方版本，与图片同步的“沿用解析版本”策略不一致。
3. TableCfg 上传前允许失败的 `lsf/cat` 没有区分“明确不存在”和“网络/鉴权失败”。
4. data 站作为并发置信源依赖 CDN 及时反映 R2 更新；时间戳和 no-cache 只能降低缓存概率，不等同于条件写入或强一致读取。

### 低优先级/性能

1. Json prepare 的多轮本地 MD5 可合并。
2. GUI 资产页说明仍称从 R2 读取索引，应改为 data 站，避免误判耗时来源。
3. 资产比较只读 data 站却要求本地 rclone 存在，可以把该前置条件推迟到正式同步。
4. 图片 publish 对大输出树重新计算摘要是强授权保护，但会产生显著磁盘读取；可在保留安全边界的前提下评估更细粒度的不可变清单。

## 18. 推荐保留、可合并与建议补强

### 建议保留

- Hotfix 文件的最终 size+MD5；这是防止损坏 VFS 的核心校验。
- 历史 map 的 manifest schema、size、SHA256 和 entryCount 对齐。
- 图片发布授权对 map、jar、输出树的本地摘要检查。
- 正式资产同步开始时对比较计划索引 revision+digest 的复核。
- TableCfg manifest 上传后回读，以及删除后 manifest/目录回读。

### 可合并或复用

- AutoWatch 把已取得的 `LatestInfo` 注入 Pipeline，避免更新触发时重复 Seed+Hotfix。
- 纯 Json 资产计划保存已确认版本并在同步时沿用；若确实需要版本锁，可改为可配置而不是无条件复查。
- 同一 GUI 会话内短时间共享已校验的 data 站资产索引响应，但必须定义最大有效期并在写入前保留一次并发核验。
- Json prepare 合并组装后的重复 MD5 遍历。

### 建议补强

- 资产索引与 map manifest 上传后至少回读目标对象并比较 digest；无需扫描桶。
- map manifest 更新增加上传前最后一次远端 digest/revision 比较，或采用 R2/S3 条件写入机制。
- TableCfg 上传前只把明确 not-found 当作不存在，其他 rclone错误直接上报。
- UI 日志明确区分“读取索引”“本地MD5扫描”“实际上传”“远端回读”，便于定位时间消耗。
